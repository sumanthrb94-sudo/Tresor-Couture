The problem

An atelier selling five-figure bridal lehengas needed to sell online without surrendering a commission on every order, and without hiring an operations team. That put the load on the software: it had to track stock, take payment, answer customers, process returns and produce a tax invoice that satisfies Indian GST — all operated by one person, often from a phone.

The interesting constraint was cost. No always-on backend, no per-seat SaaS. Which meant the browser writes to the database directly — and that is only defensible if the authorization rules are genuinely airtight.

What was built

Storefront

Catalogue with category and design-level filtering, product pages with colourways and stock-aware quantity controls, cart, wishlist, coupons, address book, three-step checkout.

Payments

Razorpay, with the server as the authority: order amounts are recomputed server-side from the catalogue, and the payment signature is HMAC-verified before an order is ever marked paid.

Real-time support

Per-order chat between customer and atelier over Firestore listeners, with unread badges on both sides. Signed-in only, so every message is attributable.

Returns & refunds

A complete RMA lifecycle — request, approve, pickup, received, refunded — with the seven-day window enforced in the database rules, not just the interface.

GST compliance

Tax invoices with HSN codes and a CGST/SGST split. Legal identifiers are format-checked and cross-validated; the invoice omits a tax number rather than printing a placeholder.

Operations console

Fourteen sections: dashboard, products, inventory, orders, returns, billing, CRM, support inbox, coupons, reviews, compliance, delivery, bulk email, catalogue SEO.

Architecture

FrontendReact 19, Vite, TailwindStrict typing across the whole domain model
DataFirestore, browser-directNo always-on backend to pay for or operate
Authorizationfirestore.rulesThe rules are the security boundary
Server logicVercel functionsOnly where a secret or an authority decision is needed
PaymentsRazorpayServer-side amount recomputation, HMAC verification
TestingPlaywright + emulatorsReal rules, real listeners, two concurrent browsers

Because the browser writes to Firestore directly, authorization lives in the rules file and the test suite attacks it: a second customer account is used on every run to prove one customer cannot read another's orders, chats or returns. Serverless functions exist only where the browser must not be trusted, and each runs the same chain — origin allowlist, CSRF double-submit token, method check, rate limit, then Firebase ID-token auth. Stock is decremented inside a transaction, so an order cannot be placed against inventory that no longer exists.

Verification

Every release is gated by a Playwright suite running against the Firebase Emulator Suite loading the real production rules. Each run emits PDF reports with embedded screenshots and manual reproduction steps, versioned in the repository.

A separate Postman collection covers the serverless endpoints' security contract, and every assertion in it is negative — forged payment signature, unsigned webhook, anonymous order, missing CSRF token, non-admin bulk email, foreign origin. No request in that folder may ever succeed, which is what makes it safe to run against production.

Known limitations

  • The hash router costs organic search. Fragment URLs are not indexed as separate pages, so product pages are currently invisible to search engines. Migrating to history routing with prerendering is the planned fix.
  • Rate limiting degrades without Redis. With no shared store configured, the limiter is per-instance rather than global — a soft guard against bursts, not a hard guarantee.
  • Refund money movement is manual by design. The workflow tracks state; a human moves the money.
